### Contexto de RLS (§3.2)
```csharp
public const string SqlContexto =
    "SELECT set_config('app.perfil', @perfil, true), set_config('app.usuario_id', @usuario_id, true)";
```
- Ordem: abre a conexão → `BEGIN` → `SqlContexto` (parâmetros `text`) → ação → `COMMIT`. Em exceção, o `await using` da transação faz o `ROLLBACK`.
- **Nenhum `set_config(..., false)` nem `SET` de sessão** em todo o código. Os testes verificam o texto (`true` nas duas chamadas, sem `false`/`SET`) e que perfil e id vão como parâmetros, sem concatenação.
- `cliente` e `usuario_cliente` só são consultadas via `ExecutarComContextoAsync`. A tabela `usuario` (sem RLS) é lida fora do contexto apenas pelo `UsuarioAtualServico`. Nos endpoints de admin, ela é lida dentro da transação com contexto de administrador.

### Identidade (§3.3)
- OID: claim `http://schemas.microsoft.com/identity/claims/objectidentifier` ou `oid`. E-mail: `preferred_username` → `email` → `upn`, com `trim` + minúsculas.
- Busca por `entra_oid`; se não achar, por `lower(email)`:

  | Situação | Resultado |
  |---|---|
  | Achou pelo OID | ok |
  | Achou por e-mail e `entra_oid` nulo | grava o OID (`UPDATE ... WHERE id = @id AND entra_oid IS NULL`) |
  | Achou por e-mail com **outro** OID | nega; o log de segurança registra só o id do usuário |
  | Não achou | não autorizado |
- `ultimo_login_em`: só para usuário ativo, e no máximo 1x a cada 10 min. A comparação usa o valor lido, então não há UPDATE em toda requisição.

### Barreira e autorização (§3.3/§3.4)
- **Middleware** depois de `UseAuthentication`. Para `/api/*`, exceto `/api/health*` e `/api/auth/me`:

  | Situação | Resposta |
  |---|---|
  | Autenticado sem cadastro ativo | 403 `{ "codigo": "USUARIO_NAO_AUTORIZADO" }` |
  | Sem banco CloudVista | 503 `{ "erro": "Banco CloudVista não configurado." }` |
  | Falha ao consultar o usuário | 503 com mensagem genérica (detalhe no log) |
  | Não autenticado | segue para o filtro global, que responde **401** como antes |
- **Políticas** `Administrador`, `Analista` e `Autorizado`, com handler que lê o perfil do `UsuarioAtualServico` (banco). Os controllers de admin usam `[Authorize(Policy = "Administrador")]`. `Analista` e `Autorizado` já estão registradas para os próximos MDs.

### Endpoints (§3.5)
- **`GET /api/auth/me`**: `{ autorizado, nome, email, perfil, usuarioId, clientes[{id,nome,apelido}] }`. Os clientes vêm pelo contexto RLS (admin = todos os ativos; demais = vinculados). Não autorizado → 200 com `autorizado: false`, mais nome e e-mail das claims para a tela.
- **Clientes**:
  - `GET ?incluirInativos=`, `POST`, `PUT /{id}`, `PATCH /{id}/ativo`.
  - Validações: nome ≤ 150; apelido `^[a-z0-9-]+$` ≤ 60; documento só dígitos ≤ 20, vazio → null.
  - Apelido duplicado (23505) → **409** "Já existe um cliente com o apelido "x"."
  - Id inexistente → 404.
- **Usuários**:
  - `GET`, `POST`, `PUT /{id}` (sem e-mail), `PATCH /{id}/ativo`.
  - E-mail validado e normalizado; duplicado → **409**.
  - Vínculos: `CLIENTE` precisa de ≥ 1 cliente **ativo**; `ANALISTA_FINOPS` aceita 0..N; `ADMINISTRADOR` tem os vínculos sempre limpos. Ids inexistentes ou inativos → 400.
  - Proteções (409): não desativar a si mesmo; não rebaixar o próprio perfil; sempre ≥ 1 ADMINISTRADOR ativo.
  - Os administradores ativos são travados com `SELECT ... FOR UPDATE` na mesma transação, para duas operações simultâneas não zerarem os administradores.
  - Vínculos gravados por substituição (`DELETE` + `INSERT ... SELECT @usuario_id, unnest(@cliente_ids)`) na mesma transação, com contexto de admin.
- **`GET /api/health`**: `{ status, timestamp, cloudVistaDb: "ok" | "nao_configurado" | "erro" }` via `SELECT 1`, sem detalhe de erro.

### SQL dos cadastros (todas parametrizadas, sem `SELECT *`)
```sql
-- clientes
SELECT id, nome, apelido, documento, ativo, criado_em, atualizado_em FROM cliente WHERE (@incluir_inativos OR ativo) ORDER BY nome
SELECT id, nome, apelido FROM cliente WHERE ativo ORDER BY nome            -- /api/auth/me (RLS filtra)
INSERT INTO cliente (nome, apelido, documento, ativo) VALUES (@nome, @apelido, @documento, true) RETURNING id, nome, apelido, documento, ativo, criado_em, atualizado_em
UPDATE cliente SET nome = @nome, apelido = @apelido, documento = @documento WHERE id = @id RETURNING ...
UPDATE cliente SET ativo = @ativo WHERE id = @id RETURNING ...
SELECT id FROM cliente WHERE ativo AND id = ANY(@ids)
-- usuários
SELECT id, email, nome, entra_oid, perfil, ativo, ultimo_login_em FROM usuario WHERE entra_oid = @oid
SELECT id, email, nome, entra_oid, perfil, ativo, ultimo_login_em FROM usuario WHERE lower(email) = @email
UPDATE usuario SET entra_oid = @oid WHERE id = @id AND entra_oid IS NULL
UPDATE usuario SET ultimo_login_em = now() WHERE id = @id
SELECT id, email, nome, perfil, ativo, ultimo_login_em FROM usuario ORDER BY nome, email
SELECT uc.usuario_id, c.id, c.nome, c.apelido FROM usuario_cliente uc JOIN cliente c ON c.id = uc.cliente_id ORDER BY c.nome
SELECT id FROM usuario WHERE perfil = @perfil_admin AND ativo FOR UPDATE
SELECT id, email, nome, perfil, ativo, ultimo_login_em FROM usuario WHERE id = @id FOR UPDATE
INSERT INTO usuario (email, nome, perfil, ativo) VALUES (@email, @nome, @perfil, true) RETURNING ...
UPDATE usuario SET nome = @nome, perfil = @perfil WHERE id = @id RETURNING ...
UPDATE usuario SET ativo = @ativo WHERE id = @id RETURNING ...
DELETE FROM usuario_cliente WHERE usuario_id = @usuario_id
INSERT INTO usuario_cliente (usuario_id, cliente_id) SELECT @usuario_id, unnest(@cliente_ids)
```
Não há DELETE em `cliente` nem em `usuario`, de acordo com as permissões do `svc_cv_api`.

## 4. Desvios e decisões (com motivo)

1. **A barreira vale para todo `/api/*`, inclusive a Visão Geral.** Ela passa a exigir usuário CloudVista ativo (qualquer perfil). Sem `ConnectionStrings__CloudVista`, a Visão Geral responde 503 "Banco CloudVista não configurado". Com ela configurada, volta a mostrar "Banco de dados não configurado" (a `FinopsDb` legada), como o MD prevê.
2. **`/api/auth/me` sem banco CloudVista → 503** (o MD não definia). Responder `autorizado: false` mostraria "sem acesso" para todos, o que confundiria o diagnóstico. A tela mostra "Não foi possível validar o acesso".
3. **`ultimo_login_em` só para usuário ativo.** Usuário inativo é resolvido, mas não ganha "último login".
4. **Cliente inativo nos vínculos:** ao editar um usuário com vínculo a um cliente que foi desativado, o salvamento retorna 400 até o vínculo ser removido. A regra "todos os ids precisam estar ativos" vale também na edição. A tela mostra esse cliente como "(inativo)" para facilitar. Se preferir manter vínculos inativos na edição, é um ajuste pequeno.
5. **Desativar um cliente não altera usuários.** Um usuário CLIENTE cujo único cliente foi desativado continua ativo, mas o RLS não mostra cliente nenhum para ele. Se quiser bloquear essa desativação (409) ou avisar, me diga.
