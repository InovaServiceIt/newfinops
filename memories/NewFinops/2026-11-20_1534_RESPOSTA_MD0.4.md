### Jobs
1. **`SincronizarAgendaJob`** (começa com 60 s e depois usa `agenda.sincronizar_seg`, entre 10 e 3600):
   - Lê `job_agenda` ativa. Para cada linha, valida o cron (Quartz, **6 ou 7 campos**) e o fuso (vazio → `America/Sao_Paulo`).
   - Inválido → `warn: Agenda {id} ignorada: {motivo}`, sem derrubar o worker.
   - Cria ou **reprograma** o trigger `agenda-{id}` só quando muda a **assinatura** (cron + fuso). O misfire é `DoNothing`: se o worker estava fora no horário, não dispara atrasado em rajada.
   - Remove triggers de agendas desativadas ou excluídas.
   - Reprograma o próprio intervalo quando o parâmetro muda.
2. **`DispararAgendaJob`** (um trigger por agenda):
   - Relê a agenda (se foi desativada nesse meio-tempo, ignora).
   - Conta as contas alvo e enfileira **1 `job_execucao` por conta** (`AGENDADA`, prioridade 100, `agenda_id`, `escopo` = `parametros` da agenda, ou `{}` se inválido).
   - Log: "N job(s) enfileirado(s) de M conta(s) alvo; K já em andamento".
3. **`ZeladorJob`** (a cada 1 min):
   - `SELECT … WHERE status='EXECUTANDO' FOR UPDATE SKIP LOCKED`.
   - Último sinal = `heartbeat_em` ?? `iniciado_em` ?? `criado_em`. Passou de `fila.timeout_execucao_min` → `tentativas < fila.max_tentativas` volta para **PENDENTE** (mantém `tentativas`; limpa `executor`, `iniciado_em` e `heartbeat_em`); senão vira **ERRO** com `"Tempo de execução excedido"` e `finalizado_em`.
   - Os UPDATEs têm `AND status='EXECUTANDO'`, por segurança contra corrida com o coletor.
- **Parâmetros:** lidos de `parametro` a cada ciclo, sem cache. Ausente, inválido ou fora da faixa → padrão seguro (60 min, 3 tentativas, 60 s).
- **Falhas nos jobs:** loga só o **tipo** da exceção e o **SQLSTATE**, nunca a mensagem.

### SQL do worker
```sql
SELECT valor FROM parametro WHERE chave = @chave
SELECT id, nome, tipo_job, cliente_id, cloud_conta_id, cron, fuso, parametros::text FROM job_agenda WHERE ativo ORDER BY id
SELECT id, nome, tipo_job, cliente_id, cloud_conta_id, cron, fuso, parametros::text FROM job_agenda WHERE id = @id AND ativo
-- contas alvo (mesmo filtro na contagem)
SELECT count(*)
FROM cloud_conta cc
JOIN cliente c     ON c.id = cc.cliente_id
JOIN credencial cr ON cr.cloud_conta_id = cc.id AND cr.status = 'ATIVA'
WHERE cc.ativo AND c.ativo
  AND (@cliente_id IS NULL OR cc.cliente_id = @cliente_id)
  AND (@cloud_conta_id IS NULL OR cc.id = @cloud_conta_id)
INSERT INTO job_execucao (tipo_job, cliente_id, cloud_conta_id, origem, agenda_id, prioridade, escopo)
SELECT @tipo_job, cc.cliente_id, cc.id, 'AGENDADA', @agenda_id, @prioridade, CAST(@escopo AS jsonb)
FROM … (mesmo filtro) …
ON CONFLICT DO NOTHING
RETURNING id
-- zelador
SELECT id, tentativas, heartbeat_em, iniciado_em, criado_em FROM job_execucao WHERE status = 'EXECUTANDO' FOR UPDATE SKIP LOCKED
UPDATE job_execucao SET status = 'PENDENTE', executor = NULL, iniciado_em = NULL, heartbeat_em = NULL WHERE id = @id AND status = 'EXECUTANDO'
UPDATE job_execucao SET status = 'ERRO', erro = @erro, finalizado_em = now() WHERE id = @id AND status = 'EXECUTANDO'
```
Na tabela `credencial`, o worker lê só `cloud_conta_id` e `status`, dentro do que foi concedido.

### API (backend)
- **`POST /api/contas/{id}/credencial/testar`** agora enfileira o job:
  ```sql
  INSERT INTO job_execucao (tipo_job, cliente_id, cloud_conta_id, origem, solicitado_por, prioridade)
  VALUES ('TESTE_CREDENCIAL', @cliente_id, @conta_id, 'MANUAL', @usuario_id, 10)
  ON CONFLICT DO NOTHING
  RETURNING id
  ```
  Sem linha retornada → **409** "Já existe um teste em andamento para esta conta." Em seguida grava a auditoria `TESTE_SOLICITADO` (detalhe `job {id}`) e responde **202** `{ jobId, mensagem }`. Continuam valendo os 409 do MD 0.3 (sem credencial ou desativada).
- **`GET /api/jobs/{id}`** (Autorizado; o RLS filtra): `{ id, tipoJob, status, criadoEm, iniciadoEm, finalizadoEm, erro, resumo }`, com `resumo` como JSON. Invisível ou inexistente → 404.
- **Front:** depois de "Testar conexão", o modal acompanha o job por **polling a cada 3 s, por até ~2 min**, mostrando "na fila / em execução / concluído / falhou · erro", e recarrega o status e o histórico ao terminar.

## 4. Desvios e decisões

1. **"23505 → já existe" foi implementado com `ON CONFLICT DO NOTHING`**, e não com captura do 23505. Uma violação de unicidade **aborta a transação** no Postgres, o que impediria continuar o lote de contas (worker) e gravar a auditoria (API). Com o `DO NOTHING`, o conflito no índice único parcial simplesmente não insere: o worker conta as contas puladas e a API responde 409.
2. **Permissão em `cliente` para o `svc_cv_worker`** (ver o aviso no topo).
3. **Sem `shared/`** (seção 2).
4. **Misfire `DoNothing`** e **sincronização por assinatura**: só reprograma o trigger quando cron ou fuso mudam.
5. **Worker sem banco sai com código 1**, em vez de ficar ocioso.
6. A mensagem do 202 virou "Teste enfileirado. Ele será executado pelo coletor.", porque agora o teste vai de fato para a fila.
