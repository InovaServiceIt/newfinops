## 1. Backend (`backend/Contas/`)

| Arquivo | Conteúdo |
|---|---|
| `ContaRegras.cs` | Contratos, provedores e escopos, validação por provedor (funções puras) |
| `ContasRepositorio.cs` | SQL e transações, sempre via `ExecutarComContextoAsync` (RLS de `cloud_conta`) |
| `ContasControllers.cs` | `ContasController` (`GET /api/contas`, política **Autorizado**) e `AdminContasController` (`/api/admin/contas`, **Administrador**) |

- **Validação (backend é a autoridade):** exatamente a tabela §2 do MD.
  - OCI `TENANCY` `^ocid1\.tenancy\.oc1\.\.[a-z0-9]+$`.
  - AWS `CONTA`/`ORGANIZACAO` com 12 dígitos.
  - Azure `TENANT`/`SUBSCRICAO` com GUID, **gravado em minúsculas**.
  - GCP `ORGANIZACAO` só dígitos; `PROJETO` `^[a-z][a-z0-9-]{4,28}[a-z0-9]$`.
  - `trim` em tudo; provedor e escopo aceitos em qualquer caixa.
  - Erros 400 com prefixo do campo ("Identificador: …", "Escopo: …", "Nome: …", "Cliente: …").
- **Duplicado (23505) → 409** "Esta conta já está cadastrada (provedor + identificador).", sem revelar o cliente.
- **Cliente ativo:** checado na criação, dentro da transação (`SELECT ativo FROM cliente WHERE id = @cliente_id`); inexistente ou inativo → 400.
- **Imutabilidade:** o `PUT` só recebe `{ nome, escopo, regiaoPadrao }`; o contrato nem tem provedor ou identificador. O novo escopo precisa ser válido para o provedor **e** compatível com o identificador já gravado. Exemplos: AWS `CONTA` ↔ `ORGANIZACAO` e Azure `TENANT` ↔ `SUBSCRICAO` são aceitos; GCP `ORGANIZACAO` (numérico) → `PROJETO` é recusado.
- **`GET /api/contas`:** `clienteId`, `provedor` e `incluirInativas` opcionais. Retorna `id, clienteId, clienteNome, provedor, nome, identificador, escopo, regiaoPadrao, ativo, criadoEm, credencialStatus: null`.
- **Lista de clientes** (`GET /api/admin/clientes`) ganhou `contasAtivas`, uma subconsulta `count(*)` em `cloud_conta` ativa por cliente.

### SQL
```sql
-- listar (RLS filtra por perfil)
SELECT cc.id, cc.cliente_id, c.nome AS cliente_nome, cc.provedor, cc.nome, cc.identificador,
       cc.escopo, cc.regiao_padrao, cc.ativo, cc.criado_em
FROM cloud_conta cc
JOIN cliente c ON c.id = cc.cliente_id
WHERE (@cliente_id IS NULL OR cc.cliente_id = @cliente_id)
  AND (@provedor IS NULL OR cc.provedor = @provedor)
  AND (@incluir_inativas OR cc.ativo)
ORDER BY c.nome, cc.provedor, cc.nome
-- criar
SELECT ativo FROM cliente WHERE id = @cliente_id
INSERT INTO cloud_conta (cliente_id, provedor, nome, identificador, escopo, regiao_padrao, ativo)
VALUES (@cliente_id, @provedor, @nome, @identificador, @escopo, @regiao_padrao, true) RETURNING id
-- alterar
SELECT cliente_id, provedor, identificador FROM cloud_conta WHERE id = @id FOR UPDATE
UPDATE cloud_conta SET nome = @nome, escopo = @escopo, regiao_padrao = @regiao_padrao WHERE id = @id
UPDATE cloud_conta SET ativo = @ativo WHERE id = @id
-- contagem na lista de clientes
(SELECT count(*) FROM cloud_conta cc WHERE cc.cliente_id = cliente.id AND cc.ativo) AS contas_ativas
```

## 2. Frontend

- **Configurações → aba "Contas de cloud"** (a aba agora fica na URL, por exemplo `/configuracoes?aba=contas`):

## 4. Desvios e decisões

1. **Ativar uma conta também exige cliente ativo**, a mesma regra da criação. Desativar é sempre permitido. Sem isso daria para "ressuscitar" a conta de um cliente desativado.
2. **Filtros cliente/provedor na tela são locais:** a tela carrega a lista que o RLS permite e filtra no navegador. A API também aceita `clienteId`/`provedor` para os próximos usos (worker e telas maiores).
3. Na página `/contas-de-cloud`, as opções do filtro de cliente vêm das próprias contas visíveis. Assim, analista e cliente só veem nomes de clientes a que já têm acesso.
