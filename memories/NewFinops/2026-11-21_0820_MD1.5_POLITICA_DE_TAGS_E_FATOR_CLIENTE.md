## Parte A — Decisão do HLGDR: perfil CLIENTE vê **sempre o valor com fator**
Hoje o CLIENTE vê o custo de nuvem **sem** fator (Visão Geral e Explorador). Isso expõe o custo real e, por tabela, a margem da Service. **Mude para:**
- **CLIENTE:** valores **sempre** com fator, aplicado no servidor, com a mesma `FatorRegras.Aplicar`. **Nunca** devolva o fator, o custo bruto ou qualquer campo que permita calculá-los: nada de `fator`, nada de `total_sem_fator`, e nada de `fatorDisponivel` como número.
- **Período sem fator vigente** para aquele cliente/conta: o CLIENTE **não vê número** naquele período. A série mostra o período como "em apuração", os KPIs mostram "—" com o texto "Valores em apuração" e o CSV omite esses períodos. Admin/analista continua vendo tudo, com o toggle atual.
- **Créditos** (`custo_credito`): o mesmo tratamento (com fator; sem fator vigente → omitido).
- O toggle de fator continua só para admin/analista (já é assim).
- A DDL abaixo adiciona `p_fator_cliente_api_leitura_visivel` (SELECT por `app_cliente_visivel`), porque a API precisa ler o fator do próprio cliente para aplicar no servidor. O endpoint `/api/fator-cliente` **continua só admin/analista**: confira com um teste.
- **Testes obrigatórios:**
  - CLIENTE recebe o mesmo valor que o admin recebe com o toggle ligado;
  - CLIENTE sem fator vigente → nenhum número;
  - o JSON de resposta do CLIENTE não contém as chaves `fator`, `semFator`, `custoNuvem` (asserção por nome de propriedade, em todos os endpoints de custo: Visão Geral, Explorador, exportar).

## Parte B — Política de tags por cliente

### B.1 Tabelas (DDL executada pelo HLGDR — **não recriar**)
- **`tag_politica`**: `id`, `cliente_id`, `chave` (mesma regex da Governança, com CHECK no banco), `valores_permitidos text[]` (nulo = qualquer valor não vazio), `descricao`, `ativa`, `criado_em/por`, `atualizado_em/por` (e-mail, como no `fator_cliente`). Única por (`cliente_id`, `chave`).
  - **Sem DELETE:** "remover" = `ativa = false`; reativar = `ativa = true`.
  - Escrita só por ADMINISTRADOR/ANALISTA_FINOPS (RLS). CLIENTE só lê.
- **`tag_conformidade_dia`**: PK (`cliente_id`, `dia`); colunas `total`, `conformes`, `com_alguma_tag`, `por_chave jsonb` (`{"ns.k": {"presentes": n, "fora_da_lista": n}}`), `chaves text[]` (as chaves ativas usadas no cálculo) e `calculado_em`. **Só o worker escreve.**

### B.2 Regras de conformidade
- O universo são os recursos ativos do cliente (`removido_em IS NULL`).
- Um recurso é **conforme** se, para **toda** chave ativa da política, tem a tag (defined `ns.k` ou freeform `k`) com valor não vazio e, quando `valores_permitidos` não for nulo, com um valor da lista. A comparação usa a **mesma normalização das variações** (caixa, espaços, acentos).
- Tags automáticas **nunca** satisfazem a política: use a regra compartilhada do ajuste.
- `fora_da_lista` = tem a chave, mas o valor não está em `valores_permitidos`.
- Cliente sem política ativa: não gera snapshot.

### B.3 Worker: snapshot de conformidade
- Depois de **cada importação com inventário** bem-sucedida, recalcule o snapshot do cliente com `dia` = data de `coletado_em` em America/Sao_Paulo. Use upsert; o último cálculo do dia vence.
- Política alterada: a cada ciclo do `ImportarColetasJob`, se existir `tag_politica.atualizado_em` > `calculado_em` do snapshot de **hoje** (ou não houver snapshot de hoje e houver inventário), recalcule o de hoje. É barato, porque é uma consulta agregada por cliente.
- Tudo agregado no SQL (sem trazer recursos para o C#), parametrizado.
- Falha no snapshot **não** derruba a importação: registra aviso no `resumo.importacao` e segue (fica fora da transação do custo/inventário, em transação própria logo depois do commit).

### B.4 API
- `GET /api/politica-tags?clienteId=` → lista com status de cada chave (presentes/ausentes/fora da lista calculados na hora sobre o inventário atual).
- `POST /api/politica-tags` `{clienteId, chave, valoresPermitidos?, descricao?}` → 201; chave duplicada → 409; regex inválida → 400. Admin/analista.
- `PUT /api/politica-tags/{id}` → altera valores/descrição/ativa. Admin/analista.
- `GET /api/politica-tags/evolucao?clienteId=&de=&ate=` → série diária de `tag_conformidade_dia` (máx. 366 dias).
- Log estruturado de alteração (usuário, cliente, chave, antes/depois), sem dado sensível.

### B.5 Tela (dentro de `/governanca-de-tags`)
- **Aba "Política"** ao lado da análise atual:
  - tabela de chaves (chave, valores permitidos em chips, descrição, ativa, % presentes);
  - botões "Adicionar chave" e "Editar" (só admin/analista);
  - em "Chaves encontradas", ação "Adicionar à política" por linha;
  - ao criar a chave, sugestão dos valores mais usados para `valores_permitidos`.
- **A conformidade da política passa a ser o padrão** quando o cliente tem política ativa. As chaves escolhidas na URL continuam valendo como "análise ad hoc" (chip "Ad hoc" e botão "Voltar para a política").
- **Card "Evolução"**: linha da % de conformidade por dia (`tag_conformidade_dia`), com a meta tracejada em **80%** (valor fixo nesta fase; vira configuração depois). Com menos de 2 pontos, mostra "A evolução aparece a partir do segundo dia de coleta".
- **CLIENTE**: vê a política, a conformidade e a evolução, sem botões de edição.
