## 0. Arquitetura (decidida — substitui o Celery do legado)

```
cloudvista-worker (.NET 8 Worker Service + Quartz.NET)   ← ESTE MD
   │  lê a agenda (job_agenda) e enfileira job_execucao (PENDENTE)
   ▼
cloudvista-collector (Python, MD 0.5)  — consome a fila com FOR UPDATE SKIP LOCKED,
   │  decifra a credencial, roda o coletor do Maurício, grava coleta_bruta, status COLETADO
   ▼
importador C# (Fase 1, no worker)  — COLETADO → IMPORTANDO → IMPORTADO
```
- **Sem broker** (nada de Redis/RabbitMQ): a fila é a tabela `job_execucao`.
- **Agenda no banco** (regra de ouro): mudar horário é UPDATE, não deploy.
- O worker **não** tem chave mestra nem credenciais de cloud. Conecta com `svc_cv_worker` (`ConnectionStrings__CloudVista`).

## 1. Tabelas (DDL será executada pelo HLGDR — não recriar; você não acessa o banco)

**`job_agenda`**: `id`, `nome` varchar(100), `tipo_job` (`COLETA_CUSTO`,`COLETA_INVENTARIO`,`COLETA_COMPLETA`), `cliente_id` null, `cloud_conta_id` null (ambos null = todas as contas ativas), `cron` varchar(100) (Quartz, 6–7 campos), `fuso` varchar(50) default `America/Sao_Paulo`, `parametros` jsonb default `{}`, `ativo`, `criado_em`, `atualizado_em`, `atualizado_por` varchar(254).

**`job_execucao`** (a fila): `id`, `tipo_job` (os 3 acima + `TESTE_CREDENCIAL`), `cliente_id`, `cloud_conta_id`, `origem` (`AGENDADA`,`MANUAL`,`SISTEMA`), `solicitado_por` FK usuario null, `agenda_id` FK null, `prioridade` smallint default 100 (**menor = mais urgente**; manual = 10), `escopo` jsonb default `{}`, `status` (`PENDENTE`,`EXECUTANDO`,`COLETADO`,`IMPORTANDO`,`IMPORTADO`,`CONCLUIDO`,`ERRO`,`CANCELADO`), `tentativas` smallint, `executor` varchar(100), `coletor_versao` varchar(30), `criado_em`, `iniciado_em`, `heartbeat_em`, `coletado_em`, `finalizado_em`, `erro` varchar(1000), `resumo` jsonb.
- Índice **único parcial** `(cloud_conta_id, tipo_job) WHERE status IN ('PENDENTE','EXECUTANDO')` → impossível duplicar job em andamento (trate 23505 como "já existe").
- Índice da fila: `(prioridade, criado_em) WHERE status = 'PENDENTE'`.

**`coleta_bruta`**: `id`, `job_execucao_id` UNIQUE, `formato` (`JSON_GZIP`), `tamanho_bytes`, `sha256`, `conteudo` bytea, `criado_em`. Gravada pelo coletor (MD 0.5); lida pelo importador (Fase 1). A API não acessa.

**Parâmetros semeados em `parametro`:** `fila.timeout_execucao_min` = 60 · `fila.max_tentativas` = 3 · `coleta.manual.intervalo_minimo_min` = 15 · `coleta.manual.perfis_permitidos` = `["ADMINISTRADOR","ANALISTA_FINOPS"]` (JSON) · `agenda.sincronizar_seg` = 60.

**Permissões:**
- worker: `job_agenda` SELECT · `job_execucao` SELECT/INSERT/UPDATE · `cloud_conta` SELECT · `credencial` SELECT (`id, cloud_conta_id, tipo, status`) · `coleta_bruta` SELECT · `parametro` SELECT. RLS liberado (sistema).
- API: `job_agenda` SELECT/INSERT/UPDATE (RLS: lê ADMIN e ANALISTA; grava só ADMIN) · `job_execucao` SELECT/INSERT (RLS: lê quem enxerga o cliente; insere ADMIN/ANALISTA, ou qualquer perfil que enxergue a conta quando `tipo_job = 'TESTE_CREDENCIAL'`).
- coletor (MD 0.5): `job_execucao` SELECT/UPDATE · `coleta_bruta` INSERT.

## 2. Projeto `worker/`

- Novo projeto **`worker/CloudVista.Worker.csproj`** (.NET 8 Worker Service) + **`worker/Dockerfile`** próprio (o HLGDR criará o recurso `cloudvista-worker` no Coolify apontando para esse Dockerfile). Se for útil compartilhar código com o backend (ex.: `NpgsqlDataSource`, `LogSeguro`), crie `shared/CloudVista.Shared.csproj` — sem quebrar o build/Dockerfile atual do backend.
- Sem HTTP (não precisa de porta). Logs estruturados no console, **sem segredo**.
- Quartz.NET **em memória** (RAMJobStore, 1 instância). A fonte da verdade é `job_agenda`.

### Jobs internos do worker
1. **`SincronizarAgendaJob`** (a cada `agenda.sincronizar_seg`): lê `job_agenda` ativa e recria/atualiza os triggers Quartz (cron + fuso). Cron inválido → log de aviso com o `id` da agenda e ignora (não derruba o worker).
2. **`DispararAgendaJob`** (um trigger por linha da agenda): resolve as contas alvo — ativas, de cliente ativo, filtradas por `cliente_id`/`cloud_conta_id` se informados, **com credencial `status = 'ATIVA'`** — e insere 1 `job_execucao` por conta (`origem = AGENDADA`, `prioridade = 100`, `agenda_id`). Conflito no índice único = já existe job em andamento → pula (log informativo).
3. **`ZeladorJob`** (a cada 1 min): `EXECUTANDO` com `heartbeat_em` (ou `iniciado_em`) mais antigo que `fila.timeout_execucao_min` → se `tentativas < fila.max_tentativas` volta para `PENDENTE` (mantém `tentativas`), senão `ERRO` com `erro = "Tempo de execução excedido"` e `finalizado_em`.
- Parâmetros lidos de `parametro` a cada ciclo (sem cache longo), com defaults seguros se faltarem.

## 3. Mudança na API (backend)

- `POST /api/contas/{id}/credencial/testar` (do MD 0.3) passa a **enfileirar** `job_execucao` (`tipo_job = TESTE_CREDENCIAL`, `origem = MANUAL`, `prioridade = 10`, `solicitado_por`) + auditoria `TESTE_SOLICITADO`. Já existe teste em andamento → **409** "Já existe um teste em andamento para esta conta." Resposta 202 com o `id` do job.
- `GET /api/jobs/{id}` — **Autorizado** (RLS): `status, criadoEm, iniciadoEm, finalizadoEm, erro, resumo` (para a tela acompanhar o teste por polling).
- Sem tela de agenda nem "Coletar agora" neste MD (isso é o MD 0.6).
