## 1. Connection string inválida expõe a senha no log (CRÍTICO)

No aceite, com a `ConnectionStrings__CloudVista` digitada errada, o log do Coolify mostrou:

```
fail: Finops.Backend.Infrastructure.CloudVistaDb[0]
      ConnectionStrings:CloudVista inválida. Endpoints do CloudVista responderão 503.
      System.ArgumentException: Couldn't set <TRECHO DA SENHA>;password (Parameter '<TRECHO DA SENHA>;password')
```

A `ArgumentException` do `NpgsqlConnectionStringBuilder` carrega **trechos da connection string (incluindo a senha)** na mensagem e no `ParamName`. Logar a exceção inteira vaza o segredo.

**Corrigir em `CloudVistaDb` e em `FinopsDb`:**
- No `catch` de connection string inválida, **não** passar a exceção ao logger nem logar `ex.Message`/`ParamName`. Logar só: `"ConnectionStrings:{Name} inválida (formato). Endpoints responderão 503."` + o **tipo** da exceção (`ex.GetType().Name`).
- Revisar todo `LogError(ex, ...)` que possa envolver `NpgsqlConnectionStringBuilder`/abertura de conexão: `NpgsqlException`/`PostgresException` de conexão são seguras (não trazem senha), mas a de **parse** não é. Se quiser um helper, crie `LogSeguro.ExcecaoConexao(...)`.
- Teste unitário: construir `CloudVistaDb` com uma connection string inválida contendo `Password=SEGREDO123;xx` e um logger de teste → assert que **nenhuma** entrada de log contém `SEGREDO123`.

## 2. Aviso ao desativar cliente (desvio 5 da sua resposta)

Ao desativar um cliente que é o **único cliente ativo** de algum usuário `CLIENTE` ativo:
- A API **permite**, mas a confirmação do front deve avisar antes: "Atenção: N usuário(s) do perfil Cliente ficarão sem acesso a dados (este é o único cliente deles): <nomes>." Para isso, `GET /api/admin/clientes/{id}/impacto-desativacao` → `{ usuariosAfetados: [{ id, nome, email }] }` (contexto RLS de admin).
- Mantidas as demais decisões da sua resposta (desvios 1 a 4 aceitos).
